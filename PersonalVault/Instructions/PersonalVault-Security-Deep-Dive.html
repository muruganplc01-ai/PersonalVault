Exact mechanisms, not marketing claims

Personal Vault — Security Deep Dive

What encrypts what, with which algorithm and key size; exactly why the publicly hosted GitHub Pages share page and its Google Apps Script backend are safe despite being visible to anyone; and a plain accounting of what this design does not protect against.

Quick answers — read this first

Where is the master password saved? Nowhere. It is never written to disk, never stored in the vault file, never logged anywhere. It exists only as a value held in memory for as long as the vault stays unlocked, and is used to derive an AES key via PBKDF2 every time the vault is saved (section 2) — the password itself cannot be recovered from anything on disk, even the encrypted vault file.

How is the vault (vault.pvlt) encrypted? AES-256-GCM, with the key derived from the master password via PBKDF2-HMAC-SHA256 (300,000 iterations, a fresh random salt on every save). Full detail in section 2.

How does a one-time share link actually work? See section 4 for the full step-by-step flow. In short: a fresh random key encrypts just that one account, the ciphertext goes to a Drive file that's never made public, the link carries the file id and key only in the URL fragment (never sent to any server), and a Google Apps Script deletes the file the instant it's first read.

Is there anything dangerous in the public docs/share/index.html? No. The only "live" value in that file is the Apps Script Web App URL — not a secret, since it can only trigger "serve once, then delete" on a file id it doesn't already know. No API keys, no OAuth secrets, no vault data live in that file. See section 5.

Was anything sensitive ever committed to the public GitHub repo? Checked directly against the full git history: credentials.json, vault.pvlt, drive-token/, and settings.json have never been committed, at any point. One Google API key was briefly committed during development and later replaced entirely by the Apps Script design — see the audit note in section 5 for what was done about the leftover copy in git history.

Is two-factor authentication a real second factor, or just an extra click? Real — the TOTP secret is stored outside the vault entirely (Windows DPAPI, tied to this PC), so decrypting the vault with the master secret does not also hand over what's needed to generate a valid code. Full reasoning in section 8.

1. Threat model

✓ Defends against

  • Someone obtaining vault.pvlt (stolen laptop, compromised Drive account) without the master secret
  • Someone obtaining a share link's Drive file id without also having the URL's key fragment
  • Network eavesdropping on either the vault sync or a share (TLS end to end)
  • Undetected tampering with an encrypted file or a share blob (GCM authentication tag)
  • A share link being read by more than one party (Apps Script trash + isTrashed() check, under a script-wide lock)

✕ Does not defend against

  • Someone who has your master secret
  • A memory-dump/debugger attack on a running, unlocked instance
  • A compromised Google account with Drive access already granted (the file is still useless without the secret, but this is out of scope of the app itself)
  • A compromised GitHub account (could tamper with the Pages site or the Apps Script deployment)
  • A weak master secret that technically satisfies the length/character rules (e.g. Password123!)

2. Vault encryption, exactly

Algorithm

AES-256-GCM (Galois/Counter Mode) — an AEAD (authenticated encryption with associated data) cipher. Unlike AES-CBC, which needs a separate MAC bolted on to get integrity, GCM produces confidentiality and tamper-detection from one pass.

Key derivation

PBKDF2-HMAC-SHA256, 300,000 iterations, a fresh random 128-bit (16-byte) salt generated on every single save — never reused, even across saves of the same vault under the same secret. 300k iterations sits well above common current baseline recommendations for PBKDF2-SHA256, deliberately making a brute-force attempt against a stolen file slow.

Nonce & tag

A fresh random 96-bit (12-byte) nonce per encryption (the NIST-recommended size for GCM), generated via a CSPRNG — nonce reuse under the same key would catastrophically break both confidentiality and authentication, so a new one is drawn every time, never derived from anything predictable. A 128-bit (16-byte) authentication tag means any single-bit change to the ciphertext, nonce, or tag causes decryption to throw rather than silently return corrupted data.

On-disk format

"PVLT" (4 bytes) | version (1) | salt (16) | nonce (12) | tag (16) | ciphertext (rest)

Fixed-size header fields — no length-prefixing needed to parse it back apart.

🔒 No custom or third-party crypto code: AesGcm/ Rfc2898DeriveBytes are .NET's own primitives, which call into Windows' native CNG/BCrypt library underneath — this keeps the implementation surface area to what Microsoft and the OS vendor maintain, not this project's own cipher code.

3. Share-link encryption, and how it differs

A share has no password of its own, so there's nothing to run PBKDF2 against. Instead: a fresh 256-bit key straight from a CSPRNG, used exactly once, never written to disk, never logged, discarded the moment the link is built. Same AES-256-GCM primitive, same 96-bit nonce / 128-bit tag sizing as the vault.

On-disk format — deliberately different field order

"PVSH" (4 bytes) | version (1) | nonce (12) | ciphertext (N) | tag (16)

Ciphertext-then-tag here, versus tag-before-ciphertext in the vault format — not an inconsistency, a requirement: the browser's crypto.subtle.decrypt expects ciphertext and tag concatenated as one buffer in exactly that order, so the viewer page can hand it the bytes as received with zero reassembly.

Key transport: the URL fragment

The raw key is base64url-encoded into the link after a #. Fragments are defined by the URL specification to never be sent by a browser to any server — not in the request line, not in headers, not in Referer. Neither GitHub Pages' CDN nor the Apps Script backend nor any network observer between the recipient and either of them ever sees the key. This is the entire basis for calling the decryption "client-side" / "zero-knowledge": literally nothing with network visibility can derive it.

4. The complete share-link flow, step by step

Everything that happens between clicking Share... and a recipient seeing the account, in order.
1

Create the link (desktop app)

You select an account → pick an expiration (1 hour to 7 days) → Create Link. The app builds a small payload from just that one account (name, username, password, extra fields, bank sub-accounts, the expiration time) — nothing else in the vault is touched.

2

A brand-new key, used once

A fresh random 256-bit key is generated — unrelated to your master password, never derived from anything, used only for this one share and then discarded (see section 3 for why this is a different scheme from the vault's).

3

Encrypt, then upload as a PRIVATE file

AES-256-GCM encrypts the payload with that key. The ciphertext is uploaded to your own Google Drive as a brand-new file with no sharing permission granted at all — not even "anyone with the link." Nobody can read it directly, not even you without your own Drive sign-in.

4

Build the link

https://<you>.github.io/PersonalVault/share/#id=<fileId>&key=<theKey>&exp=<time> — the file id and key sit after the #, a URL fragment. Browsers never transmit anything after # to any server, so this key never travels over the network at all, to anyone, at any point. The link is copied to your clipboard.

5

Recipient opens the link

Their browser loads the static index.html page. Its JavaScript reads the id and key straight out of the URL fragment, locally — this never leaves their browser.

6

The page asks Apps Script for the file — without the key

The page calls your Google Apps Script Web App, passing only the file id. The key is deliberately not sent in this request either — Apps Script never sees it, ever.

7

Apps Script serves it once, then destroys it

Running under your own Google identity, the script finds the file, reads its (still-encrypted) bytes, immediately trashes the file, and returns the bytes. If the file is already gone (already opened once, expired, or revoked), it replies GONE instead — see section 5, step 6 for exactly how "only once" is enforced.

8

Decrypt entirely inside the recipient's browser

The page decrypts the returned bytes using the key it already had from step 5, via the browser's built-in Web Crypto API (crypto.subtle.decrypt) — nothing server-side ever performs or sees this decryption. The fields are rendered with per-field copy buttons.

9

Links nobody ever opens

A timer in the desktop app (every 15 minutes) independently deletes any Drive file whose expiration has passed and was never opened — a safety net for a link that's simply forgotten about, on top of the immediate one-time consumption in step 7.

5. Why a fully public GitHub Pages page is safe

Walking through every piece of information a random visitor can actually see, and why none of it is exploitable.
1

The JS source is 100% public (view-source works)

By design, nothing secret is embedded in it. An earlier version of this design embedded a restricted Google API key directly in the page; the current design removed that entirely in favor of the Apps Script backend, so there is now nothing at all in the public page worth protecting. Knowing the exact algorithm and blob layout (published above) gives an attacker nothing without a key — this follows Kerckhoffs's principle: security must rest on the key, never on the algorithm being secret.

2

The Apps Script Web App URL is knowable too — and that's fine

Calling it does nothing useful without a valid, not-yet-consumed Drive file id. Knowing a file id alone, without the URL fragment's key, yields only ciphertext.

3

Drive file ids are not guessable

Google-generated, long, high-entropy, not sequential, not derived from anything public (account name, timestamp, etc). There is no practical way to enumerate them.

4

The Drive file itself is never publicly shared

GoogleDriveSync.UploadShareAsync grants no "anyone with the link" permission at all. The Apps Script can read it purely because it runs "Execute as: Me" — a privilege scoped to that deployed script's own execution context, never exposed to whoever calls the Web App.

5

Even the backend only ever sees ciphertext

Code.gs has no access to, and never receives, the decryption key — it only reads and returns raw encrypted bytes. Even a tampered or malicious deployment could at most exfiltrate ciphertext it already legitimately serves, never plaintext, since decryption happens exclusively in the recipient's browser afterward.

6

First-read consumption is enforced, not assumed

LockService.getScriptLock() serializes every execution of the same deployed script (script-wide, not just per-file), so two near-simultaneous opens of one link cannot both read the file before either one trashes it. file.isTrashed() is checked explicitly on every request, because DriveApp.getFileById() does not throw for a trashed file — skipping that check was a real bug caught and fixed during this project's own testing.

7

GitHub Pages itself runs no server-side code

Pure static file hosting — it cannot be tricked into doing anything beyond serving the same public HTML/JS to everyone, which is harmless by construction.

8

Transport is TLS end to end

Both github.io and script.google.com are served over HTTPS — defense in depth on top of the fragment-never-transmitted property, not the primary protection.

✓ Audited 2026-09-23: confirmed the repo is public via the GitHub API, and searched the entire git history for credentials.json, vault.pvlt, drive-token/, and settings.json — none has ever been committed, at any point. One Google Drive API key from an earlier version of this design (before the Apps Script rework) was found still present in an old commit even though the current code no longer uses it; it has since been revoked in Google Cloud Console, closing that off completely.

7. In-memory hygiene, and its honest limit

CryptographicOperations.ZeroMemory is called on derived AES keys and decrypted plaintext buffers immediately after use, throughout VaultCrypto, ShareCrypto, and VaultStorage.

⚠️ The master secret itself is a .NET string — immutable, not zeroable, and the garbage collector does not scrub freed memory. A memory-dump or debugger attack against a running, unlocked process is not defended against by this design. Auto-lock (10 minutes idle by default) shrinks the exposure window; it does not close it. This is a stated, deliberate trade-off, not an oversight — hardening every in-memory secret against a forensic memory dump would require a fundamentally different (and much more invasive) approach than a normal desktop app typically takes.

8. Two-factor authentication - why it's real, not theater

An optional second factor (Profile → Two-Factor Authentication...) - a TOTP authenticator app or an emailed code - sits after the master secret. The one design question that decides whether this is a genuine second factor or just an extra click: can someone who already has vault.pvlt and the master secret also generate a valid code? If the second factor's material lived anywhere reachable by decrypting the vault, the answer would be yes, and "two steps" would only ever cost an attacker one extra click.

TOTP: the secret lives outside the vault entirely

The raw TOTP secret is stored DPAPI-protected (ProtectedData.Protect, DataProtectionScope.CurrentUser) in its own file, never inside vault.pvlt. Someone who steals the vault file (or a Drive copy) and even correctly guesses the master secret still cannot compute a valid TOTP code without also being logged into this exact Windows account on this exact machine - DPAPI ties the key to the OS user profile that protected it. This is the load- bearing design choice that makes TOTP here a real second factor rather than a formality.

The trade-off, stated plainly: this secret does not travel to a new PC or survive a disaster-recovery restore. Ten one-time backup codes (only their SHA-256 hashes stored, inside VaultProfile so they do travel with the vault) are the recovery path - each works once, then its hash is deleted. Regenerating TOTP invalidates every old backup code at the same time, same as any mainstream provider.

Email: no shared secret at all, and a narrower Google scope

No secret to protect - a fresh random 6-digit code is generated per attempt, held only in memory, and emailed via Gmail using the exact same OAuth credential already authorized for Drive. This is only a real second factor because it depends on access to an inbox the attacker doesn't have - the vault file and master secret alone are not enough to read the code, only to trigger it being sent.

🔒 Gmail's send-only scope is requested only when Email MFA is actually turned on, not for every Drive sign-in - someone who only wants Drive backup never sees an unexpected "send email on your behalf" consent screen. See GoogleDriveSync.SignInAsync's includeGmailSendScope parameter.

Both methods share one rule

The second-factor check runs strictly after a successful decrypt but before the app treats the vault as unlocked - a wrong or cancelled code immediately drops the decrypted vault from memory and returns to the master secret prompt, the same as if the secret itself had been wrong. A decrypted vault never sits around waiting on a second factor that might fail.

9. Known limitations, stated plainly

  • No protection against a compromised end-user machine while the vault is unlocked.
  • No password-reset or key-recovery path — deliberate: there is no backdoor to build into a system that has none.
  • PasswordPolicy enforces a floor (12 characters, upper/lower/symbol), not real strength — it does not block predictable patterns.
  • The desktop app's "Shared Links..." list can lag reality (an opened link still shows "Active" until the next expiry sweep) — a cosmetic gap, not a security one; the link itself is genuinely dead the instant it's consumed.
  • TOTP two-factor doesn't survive moving to a new PC or a disaster-recovery restore, by design (section 8) — a backup code is the way back in, after which TOTP is set up fresh on that machine.
  • Email two-factor requires Drive to be connected with Gmail's send-only scope granted — there's no other zero-cost way to send the code, so it's unavailable entirely offline or without a Google account.
  • Google/GitHub account compromise is out of this app's own threat model — protect those accounts with their own strong authentication (2FA, etc).
