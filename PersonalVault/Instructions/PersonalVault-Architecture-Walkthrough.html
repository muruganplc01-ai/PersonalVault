Personal Vault — Architecture Walkthrough

What this app is, what it's built with, where every file lives, how a save actually reaches disk and Drive, and the full request path a one-time share link takes from creation to consumption.

1. What this is

A Windows system-tray app (no main window that, if closed, ends the process) that keeps one AES-256-GCM encrypted file as its single source of truth for a list of account/credential records. There is no first-party server anywhere in this system: the desktop app talks directly to Google Drive's REST API for backup, and a separate, optional feature (one-time share links) is served by a static page on GitHub Pages plus a small Google Apps Script Web App — both running under the vault owner's own accounts, not any infrastructure this project operates.

5. Vault save/load flow

1

Unlock

UnlockForm collects the secret → VaultCrypto.Decrypt derives a key via PBKDF2 using the salt stored in the file's header → AES-GCM decrypt → JSON deserialize into a VaultData object held in memory by TrayApplicationContext.

2

Edit

Forms (AccountEditForm, ProfileForm, etc.) mutate that in-memory VaultData directly. Nothing touches disk until Save.

3

Save locally

TrayApplicationContext.SaveVault() → VaultStorage.SaveLocal: serialize to JSON → VaultCrypto.Encrypt (a fresh random salt and nonce every single save, never reused) → write to a .tmp file → File.Replace into place, so a crash mid-write can never corrupt the real file.

4

Sync to Drive (fire-and-forget)

UploadToDriveAsync → GoogleDriveSync.UploadOrUpdateAsync uploads the already-encrypted bytes as-is — Drive never receives plaintext at any point. PruneOldRevisionsAsync then pins the new revision and prunes anything beyond the last 5, using Drive's own revision history as a rolling backup.

6. One-time Share Account: the complete request path

This is the part most worth understanding end to end before changing anything in it — a mistake here has real security consequences.

Solid arrows are network requests; every one of them carries a file id but never the decryption key. The dashed arrow (step 2) isn't an API call at all — it's just however you send the link (email, text, etc.); it's the only place the key exists outside your own memory, and it lives only in the part of the URL browsers never transmit.

1

Create the link (desktop app)

ShareAccountForm (expiration picker) → TrayApplicationContext.ShareAccountAsync builds a SharedAccountPayload (name, credentials, extra fields, bank sub-accounts, an embedded ExpiresUtc) and JSON-serializes it.

2

Encrypt

ShareCrypto.Encrypt generates a fresh random 256-bit key (not derived from anything — there's no password for a share) and a random 96-bit nonce, AES-256-GCM encrypts, and returns a blob: "PVSH" | version | nonce | ciphertext | tag.

3

Upload as a PRIVATE Drive file

GoogleDriveSync.UploadShareAsync does a plain Files.Create — no sharing permission is ever granted. The file is readable by nobody except the owner's own Google identity.

4

Build the link

https://<github-username>.github.io/PersonalVault/share/#id=<driveFileId>&key=<base64url-key>&exp=<unixSeconds> — the key and file id live only in the URL fragment (after #), which browsers never include in any HTTP request, to any server, ever. A SharedLink record (file id + expiry, not the key) is appended to shares.json for bookkeeping.

5

Recipient opens the link

docs/share/index.html's JS reads location.hash client-side, then fetch()es the Apps Script Web App's /exec?id=<fileId> URL — note: the key is not sent in this request at all.

6

Apps Script consumes it (Code.gs, doGet)

Runs "Execute as: Me" (the vault owner) regardless of caller. Acquires LockService.getScriptLock() → DriveApp.getFileById(id) → checks file.isTrashed() (critical: getFileById does not throw for a trashed file, so skipping this check would let a link work forever) → if fresh: reads bytes, base64-encodes them, setTrashed(true), returns the base64 text. If already trashed or the id doesn't resolve: returns the literal string GONE.

7

Decrypt client-side

The browser base64-decodes the response, splits out the nonce, and calls crypto.subtle.decrypt with the key parsed from the URL fragment back in step 5 — the only place that key ever existed after creation. Renders the fields with per-field copy buttons.

8

Safety net for links nobody opens

ShareExpiryService (desktop app, 15-minute timer) independently scans shares.json for entries past ExpiresUtc that haven't been revoked, and deletes their Drive file outright via GoogleDriveSync.RevokeShareAsync — this only matters for a link that was never opened; an opened link is already gone via step 6 regardless of whether the desktop app is even running.

⚠️ The desktop app cannot learn that a link was opened. Apps Script has no channel back to the .NET app. SharedLinksForm's "Active" status can lag reality until the next expiry sweep discovers the file is already gone — cosmetic only, the link itself is genuinely dead the instant it's consumed.
